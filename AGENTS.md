# AGENTS.md

## О проекте

URL Shortener — сервис для создания коротких ссылок и перенаправления пользователей на исходные URL.

Проект организован как TypeScript monorepo и содержит отдельные frontend и backend приложения.

## Стек

### Frontend

* Vue 3
* TypeScript
* Vite
* Pinia
* shadcn-vue

### Backend

* Node.js
* TypeScript
* Fastify
* Zod

### Database

* PostgreSQL
* Drizzle ORM

### Tooling

* pnpm workspaces
* Vitest
* ESLint
* Prettier

## Структура репозитория

```text
.
├── apps/
│   ├── web/          # Vue frontend
│   └── api/          # Fastify backend
│
├── packages/
│   └── shared/       # Общий код и контракты
│
├── package.json
├── pnpm-workspace.yaml
└── tsconfig.base.json
```

Перед изменением структуры необходимо учитывать существующие границы приложений и packages.

Не создавать новые packages без конкретной необходимости.

## Общие принципы

### Простота

Выбирать наиболее простое решение, удовлетворяющее текущим требованиям.

Не добавлять abstractions, infrastructure или dependencies для гипотетических будущих требований.

Не применять design patterns только ради использования pattern.

### Scope задачи

Изменения должны соответствовать текущей задаче.

Не выполнять несвязанный refactoring и не исправлять соседний код без необходимости для выполнения задачи.

Если обнаружена отдельная проблема, которую не требуется решать сейчас, её следует обозначить отдельно, а не незаметно расширять scope.

### Dependencies

Не добавлять новую dependency, если задача может быть разумно решена существующими средствами проекта.

Перед добавлением dependency необходимо понимать:

* какую конкретную проблему она решает;
* почему существующих средств недостаточно;
* какую стоимость она добавляет проекту.

Не заменять существующие библиотеки без явной причины.

### Shared code

Не переносить код в `packages/shared` только потому, что он потенциально может понадобиться нескольким приложениям.

Shared abstraction должна появляться после возникновения реального совместного использования или явного общего контракта.

Избегать преждевременного обобщения.

## TypeScript

Предпочитать строгую типизацию.

Не использовать `any`, если это не обусловлено конкретной технической причиной.

Не использовать type assertions (`as`) для обхода ошибок TypeScript без понимания причины ошибки.

Предпочитать вывод типов там, где явная аннотация не добавляет полезной информации.

Не дублировать runtime validation TypeScript-типами вручную, если тип может быть безопасно получен из существующей schema.

## Frontend

Frontend находится в `apps/web`.

Использовать Vue 3 Composition API.

Для новых компонентов предпочтителен `<script setup lang="ts">`.

Локальное состояние должно оставаться локальным, пока нет причины переносить его в Pinia.

Не использовать Pinia как глобальное хранилище любого состояния приложения.

Не добавлять Vue Router до появления реальной необходимости в client-side routing.

Для базовых UI primitives использовать существующие компоненты shadcn-vue, если они подходят требованиям.

Не создавать собственную реализацию стандартного UI primitive без причины.

Не изменять компоненты shadcn-vue глобально ради поведения, специфичного только для одного feature.

## Backend

Backend находится в `apps/api`.

Fastify используется как HTTP framework.

Разделять:

* HTTP concerns;
* validation;
* business logic;
* persistence.

При этом не создавать дополнительные архитектурные слои, если сложность текущего кода этого не требует.

Все внешние данные считать недоверенными.

Входящие HTTP payload, params и другие внешние значения должны проходить runtime validation.

Frontend validation не заменяет backend validation.

## Database

PostgreSQL является основным persistent storage.

Для работы со схемой и запросами используется Drizzle ORM.

Изменения структуры БД должны выполняться через migrations.

Не полагаться только на application-level проверки там, где invariant может и должен обеспечиваться самой БД.

Например, уникальность short code должна поддерживаться database constraint.

## API

API должно использовать HTTP semantics осознанно.

Не возвращать `200 OK` для всех результатов только ради упрощения frontend-кода.

Использовать подходящие status codes для успешных и ошибочных сценариев.

Не менять существующий API contract без необходимости.

При изменении contract проверить все его consumers.

## Error Handling

Не подавлять ошибки без причины.

Не использовать пустые `catch`.

Ошибки должны обрабатываться на том уровне, где имеется достаточно контекста для принятия решения.

Не раскрывать клиенту внутренние stack traces и детали infrastructure.

## Testing

Тестировать поведение, а не детали реализации.

При исправлении воспроизводимого bug по возможности сначала добавить regression test.

Приоритет тестирования:

1. критичная business logic;
2. validation;
3. API behaviour;
4. важные integration boundaries.

Не писать тест только ради увеличения coverage.

## Git

Использовать понятные небольшие commits.

Если работа связана с Jira issue, сохранять issue key в branch/commit/PR naming там, где это предусмотрено workflow проекта.

Не коммитить:

* `.env`;
* credentials;
* secrets;
* `node_modules`;
* generated/local files, не предназначенные для repository.

## Проверка изменений

Перед завершением задачи необходимо выполнить применимые проверки проекта.

Как минимум:

```bash
pnpm lint
pnpm test
```

Если настроен отдельный typecheck:

```bash
pnpm typecheck
```

Не утверждать, что проверки прошли, если они фактически не запускались.

Если проверку невозможно выполнить, явно указать это.

## Работа с документацией

Если изменение влияет на публичное поведение, API, setup или workflow разработки, проверить необходимость обновления документации.

Не документировать ещё не существующее поведение как уже реализованное.

## Безопасность

Никогда не добавлять в repository:

* passwords;
* API keys;
* access tokens;
* private keys;
* production credentials.

Использовать environment variables для конфигурации, зависящей от окружения.

`.env.example` не должен содержать реальные secrets.

## Главное правило

Не пытаться превратить небольшую текущую задачу в окончательную архитектуру всего проекта.

Сначала решить существующую проблему наиболее простым поддерживаемым способом.

Усложнение должно появляться вслед за реальными требованиями.

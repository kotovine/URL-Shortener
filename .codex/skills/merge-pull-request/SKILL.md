# Merge pull request

## Стратегия

- Для PR в `main` по умолчанию использовать **Squash and merge**, чтобы один PR оставлял один законченный коммит в истории `main`.
- Использовать другой способ merge только по явному запросу пользователя или если отдельные коммиты PR необходимо сохранить как самостоятельные этапы истории.
- Не мёржить PR автоматически: перед действием показать method merge, итоговые subject и body коммита и получить явное подтверждение пользователя.

## Итоговый коммит

- Subject формировать как `<Jira key>: <краткий результат>`; например: `KAN-5: Инициализация monorepo URL Shortener`.
- Если Jira key отсутствует, использовать краткую русскоязычную именную группу, описывающую результат. Не писать технические детали процесса, например «squash», «merge PR» или номера промежуточных коммитов.
- Если title PR соответствует этим правилам, использовать его как subject squash-коммита.
- Body добавлять только когда он сохраняет важный контекст, который будет нужен без просмотра PR. Иначе оставлять пустым для компактной истории.

## Подготовка и merge

- Проверить source и target ветки, состояние PR, список включаемых коммитов, результат проверок и возможность merge.
- Если PR не готов к merge из-за конфликтов, обязательных проверок или branch protection, сообщить причину и не обходить ограничения.
- Не изменять target branch, не выполнять rebase и не включать auto-merge без отдельного запроса пользователя.
- Удалять source branch после merge только по явному указанию пользователя.

## Отчёт

- После успешного merge сообщить URL PR, способ merge, hash итогового коммита и статус source branch.
- При ошибке остановиться, привести безопасный контекст и не повторять merge автоматически.
